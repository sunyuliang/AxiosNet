## A1 跨终端凭证只有一格

**命题**：一次尝试只能携带**一个**跨终端资源，第二个无处安放。

**取证**（反射，`A1_SingleSlotCensus`）：

| 成员 | 类型 | 说明 |
|---|---|---|
| `AxiosAttemptContext.Slot` | `IDisposable?` | 唯一的跨终端凭证槽位 |
| `AxiosAttemptResult.SlotTransferred` | `bool` | 唯一的「交给下游、别归还」标记 |

**结论：成立。** 闸门的并发槽位与流式正文的 `StreamOwner` 已经在抢这一格（库内靠
`SlotTransferred` 区分「谁是主人」）。任何新的跨终端资源（审计会话、租约、批处理句柄）
都没有位置，只能挤进同一个 `IDisposable` 或改公共契约——后者正是重构成本翻倍的地方。

**修复（2026-11-16）：** `Slot` → `Lease`，`WithSlot(IDisposable?)` → `WithLease(IDisposable)`
（`null` 抛 `ArgumentNullException`）。登记改为**追加**：`WithLease` 链式叠加，
第二个起合成 `AxiosAttemptLeases`（内部链表，最新在前），释放走登记顺序的**逆序**且幂等。
`AxiosAttemptResult.SlotTransferred` → `LeasesTransferred`，含义扩成「登记的租约全部已随正文转交」。
只登记一个租约时裸放、不包装，闸门槽位这条最常见路径的分配数为 **0**（`FirstLease_IsStoredAsIs_WithoutWrapping`
断言 `Assert.Same`）。复测：反射面 `Slot`/`SlotTransferred` 已消失，登记容量从 1 → N；
`AttemptLeaseTests` 8 条用例覆盖追加语义、逆序释放、幂等、单个抛错不跳过其余，
以及与终端 / 闸门 / 流式正文的交接（`ExtraLease_StaysWithTheStream_UntilItIsDisposed`、
`GateSlotAndExtraLease_AreBothReleased_AfterAFailure`）。

## A5 遥测实现不可替换

**命题**：`AxiosTelemetry` 是静态类，包外无法替换实现，只能靠 `ActivitySource` / `Meter` 名字订阅。

**取证**（`A5_TelemetryIsStaticAndNotReplaceable`）：

```
AxiosTelemetry: IsAbstract=True, IsSealed=True, IsStatic=True
公共构造函数：0 个
公共可写属性/字段（可用于替换实现）：0 / 0
Observability 配置叶子：Capture, OnUploadProgress, OnDownloadProgress, OnRawResponse,
                        CaptureRawResponseBody, OnSendingRequest, TimeoutMessage
```

**结论：成立。** 配置面上只有「回调」，没有「实现替换」。要用自家的指标/追踪管道
（例如公司内部 tracing 规范），只能按名字订阅再自行翻译，且无法关掉内置的那套。

**修复（2026-11-16）：** 三路输出（span / 指标 / 事件）全部改经 `IAxiosTelemetrySink` 出去，
`AxiosTelemetry.Sink` 一换即整套接管（内置那套同时停用，不是叠加）；`AxiosTelemetrySink`
是全空实现的基类，派生后只覆写关心的几个方法；`AxiosRequestTrace`（结构体句柄，默认值 = 不观测）
承载 `StartRequest` → `Stop` / `SetRequestBodySize` 的派发。默认仍是内置实现，行为不变。
复测：反射面从「0 个替换点」变成 1 个可写属性 + 1 个接口 + 1 个基类（见对照表）；
`TelemetrySinkTests` 4 条用例证明「换实现后内置 ActivitySource 一条 span 都不产」
（`CustomSink_TakesOver_AndBuiltInStopsProducingSpans` 里挂 `ActivityListener` 计数为 0）、
「`Off` 彻底关掉而请求照常成功」、「默认实现仍是内置那套」、「赋 `null` 被拒」。

## E6 用户可见消息中英混杂

**命题**：同一个 `AxiosException`、同一个错误码，消息语言不一致。

**取证**（`E6_MessageLanguageCensus`）：

| 位置 | 中文字符数 |
|---|---:|
| `AxiosException.cs`（错误文案集中地） | 2,539 |
| `AxiosClient.Validation.cs`（校验文案） | 2,913 |
| `AxiosClient.Shortcuts.cs`（重载守卫文案） | 1,868 |

同一次运行里抓到的两条 `ERR_BAD_OPTION_VALUE`：

```
中文（库自写）：
  MaxRedirects 是实例级配置（重定向由连接池 Handler 处理），按请求只能写与实例相同的值；
  当前按请求为 0，实例生效值为 5（0 表示不跟随重定向）。要改变它请新建 AxiosClient
  并在 defaults 或 ConnectionPoolOptions 上设置。

英文（BCL 原样透出）：
  The format of the HTTP method is invalid.
```

**结论：成立。** 英文用户（`README.en.md` 明确是一等目标）在日志里会拿到一半中文；
而中文用户拿到的 BCL 消息又是英文。两条消息还都长（中文那条 90+ 字），日志里噪音大。

**本轮处理：暂不修（2026-11-16 决定）。** 三条路各有代价：统一英文要把库自写的 634
条中英文案全改（还会推翻 `Request failed with status code {n}` / `timeout of {n}ms exceeded`
这类与 axios 逐字对齐的文案，连带动 120 处断言）；统一中文要把 BCL 透出的英文逐处包一层
中文上下文（英文用户更糟，且与上一条刚定下的英文文案相互打脸）；资源表按 `CultureInfo`
切换最贵，还要在 netstandard2.0 上落地。已试改一版「统一中文」并完整回滚——**不要**在没有
明确指示时重开这条线。复测口径保持不变（下面的字符统计 + 两条样例），留待定方向后一次做完。

## E7 同名前缀重载过多

**命题**：`PostAsync` 这类入口的重载数量让人只能靠猜，相邻签名语义不同。

**取证**（`E7_OverloadCensus`，反射枚举公共实例/静态方法，按名字分组）：

| 类型 | 方法名 | 方法总数 |
|---|---:|---:|
| `AxiosClient` | 14 | 70 |
| `Axios` | 16 | 60 |
| **合计** | **30** | **130** |

`AxiosClient` 的重载分布：

```
GetAsync 8、DeleteAsync 8、HeadAsync 8、OptionsAsync 8、
PostAsync 6、PutAsync 6、PatchAsync 6、RequestAsync 4、…
```

`PostAsync` 的 6 个重载（去掉返回类型后仍有成对重复）：

```
PostAsync(string url, object data, Action<AxiosConfig> configure, CancellationToken ct)  → Task<AxiosResponse>
PostAsync(string url, object data, Action<AxiosConfig> configure, CancellationToken ct)  → Task<AxiosResponse<T>>
PostAsync(string url, AxiosConfig config)                                                → Task<AxiosResponse>
PostAsync(string url, AxiosConfig config)                                                → Task<AxiosResponse<T>>
PostAsync(string url, CancellationToken ct)                                              → Task<AxiosResponse>
PostAsync(string url, CancellationToken ct)                                              → Task<AxiosResponse<T>>
```

**结论：成立，且比评估时的 123 个更多（现 130 个）。** 额外发现：**同一签名只因返回类型
不同（`AxiosResponse` vs `AxiosResponse<T>`）就成对出现**，IntelliSense 里两行几乎一模一样，
选错的后果是「拿到非泛型响应，`.Data` 变成 `object`」。

**修复（2026-11-16）：只做了「不再让人猜」，没有删重载 —— 删了会更危险。**

先按原计划动手删 `(url, AxiosConfig)`（14 个）与 `WithUrl`，删完**编译居然通过**：
`object? data` 把 `AxiosConfig` 吞了。实测下来错用分两种：

| 错用 | 修复前实际行为 |
|---|---|
| `client.PostFormAsync(url, new AxiosConfig())`（表单动词没有 config 形态） | 抛 `ERR_BAD_REQUEST`「正文序列化失败」—— 错误码与真实原因无关 |
| `Axios.GetAsync(url, new AxiosConfig())`（静态门面从来没有 config 形态） | 同上；同一行代码在实例上走的却是配置形态 |

而 `(url, CancellationToken)` 形态同理：删掉它，`PostAsync(url, ct)` 会**编译通过**并把这个令牌
当成请求正文序列化出去 —— 静默错用比多几个重载可怕得多。`CancellationToken` 的护栏早就存在
（`Shortcut` 里 `data is CancellationToken` 直接抛），只是没覆盖 `AxiosConfig`。

所以 E7 落地为：**① 把 `data` 位置的护栏扩到 `AxiosConfig`**（消息指路 `RequestAsync(config)`）；
**② README 补一张四形态决策表**（要什么 → 写哪种、`(url, config)` 只在实例的 7 个动词上有、
表单动词与静态门面走 `RequestAsync`）。**方法数保持 130 不变**：数量多的根因不是「形态多」，
而是「同一个语法在两个类型上语义不同」，这一点已由护栏 + 决策表消掉。
`ShortcutArgumentGuardTests` 4 条用例钉住「配置 / 令牌放错位置 → `ERR_BAD_OPTION_VALUE` + 一条请求都不发」
与「正常 data 不受影响」。

## E10 实例级项类型允许、运行期才拒

**命题**：7 个「只能在实例上设」的项挂在 `AxiosConfig` 上，按请求写编译通过、发请求才抛错。

**取证**（`E10_InstanceLevelItemsAreWritablePerRequest`，真实回环服务器）：

```
编译期全部放行：
  Transport.MaxRedirects=0、Transport.WithCredentials=True、Concurrency.MaxInFlight=4
运行期才被拒绝：
  ERR_BAD_OPTION_VALUE — WithCredentials 是实例级配置（影响 Cookie 容器与系统凭据），
  按请求只能写与实例相同的值；当前按请求为 True，实例生效值为 False。
  要改变它请新建 AxiosClient 并在 defaults 上设置。
```

涉及项（`AxiosClient.Validation.cs` 的守卫清单）：`Transport.Proxy` / `Credentials` /
`WithCredentials` / `MaxRedirects` / `Pool`、`Resilience.Concurrency.MaxInFlight` / `MaxQueue`。

**结论：成立。** 「这一次请求走代理」「这一次不跟重定向」这类写法在类型上完全合法，
错在几秒后才以运行时异常出现，而且错误消息只能事后补救。

**修复（2026-11-16，不留兼容层）**：七项整体搬到新建的 `AxiosClientOptions`，`AxiosConfig` 上
对应属性与 `*Set` 标记一并删除，运行期守卫（`ValidateWithCredentials` / `ValidateMaxRedirects`）
与闸门容量不一致的两条报错随之删除。复测方式从「看运行期抛不抛」变成「看 API 面在不在」：

```
AxiosConfig 上仍存在的实例级项：0 个
AxiosClientOptions 上可写的实例级项：7 个
```

新增护栏 `ClientInstanceTests.InstanceLevelOptions_AreNotOnAxiosConfig` 用反射钉住这两句；
`ProblemEvidenceTests.E10_*` 已改为同一口径的复测用例（`Assert.Empty(survivors)` + `Assert.Equal(7, …)`）。

## A8 兼容资产几乎没有行为证据

**命题**：`netstandard2.0` 资产用扩展方法补 BCL 实例方法，同一份源码在两个 TFM 静默走不同实现，
而兼容套件的用例密度不到主套件的 2%。

**取证**（`A8_CompatCoverageDensity`）：

```
Compat.Tests 源文件 7 个，用例 47 条     （主套件 2,560 条 → 1.8%）
```

`Compatibility/NetStandard20Extensions.cs` 提供的 polyfill（20 个，节选）：

```
WaitAsync(Task, TimeSpan) / (Task, CancellationToken) / (Task, TimeSpan, CancellationToken)   ← 3 个 × 泛型镜像 = 6
ReadAsync(Stream, Memory<byte>, CancellationToken)
WriteAsync(Stream, ReadOnlyMemory<byte>, CancellationToken)
Write(Stream, ReadOnlySpan<byte>)
DisposeAsync(Stream)                    ← 直接调 Dispose()，不走派生覆写
ReadAsStreamAsync(HttpContent, CancellationToken)
ReadAsByteArrayAsync(HttpContent, CancellationToken)
CopyToAsync(HttpContent, Stream, CancellationToken)
GetBytes / GetString / GetCharCount（Encoding 的 Span 重载）
StartsWith / Contains（string / ReadOnlySpan<char> 的 char 重载）
TryAdd(IDictionary) / TryRemove(ConcurrentDictionary)
CreateDelegate(MethodInfo)
```

**结论：成立。** 这些扩展方法在语义上都**可能**与 net6 的虚方法不同（最典型的是
`DisposeAsync` 落到 `Dispose()`、`ReadAsync(Memory)` 可能只读一部分），但目前只有 47 条用例
兜着，跨 TFM 的性能与行为结论缺少证据。

**修复（2026-11-16）：补语义面，不补分配面。** 分配面已由 `ShimEvidenceTests` 覆盖（`Category=Evidence`，
CI 默认过滤），缺的是「同一条业务代码在两个 TFM 上到底得到什么」：
新增 `test/AxiosNet.Compat.Tests/PolyfillSemanticsTests.cs` 10 条用例，逐条显式调用 shim
（测试工程按 net8.0 / net472 编译，写 `stream.ReadAsync(memory)` 会直接绑到 net8 的 BCL 实例方法上，
等于什么都没测——这是这批用例最容易写错的地方）：

| 用例 | 钉住的语义 |
|---|---|
| `ReadAsync_shim_返回实际读到的字节数_空区间不消耗流` | 分段读取返回实际字节数；空区间返回 0 且**不动流位置** |
| `ReadAsync_shim_对非数组支撑的_Memory_也把字节写进目标区间` | 租借缓冲路径的复制方向 / 长度（写错就是「读到 3 字节、内容是垃圾」） |
| `WriteAsync_shim_在数组与租借缓冲两条路径上都写出全部字节` | 两条路径的写出内容一致；空区间不碰底层流 |
| `Write_shim_同步重载写出全部字节_空区间不调用底层` | 同上（同步重载） |
| `DisposeAsync_shim_退化为同步释放_并立即完成` | `DisposeAsync` 落到 `Dispose()`：`await` 之前就已释放 |
| `HttpContent_shim_的读取与复制_在进入边界就尊重已取消的令牌` | `ReadAsStreamAsync` / `CopyToAsync` 的令牌只在进入边界生效 |
| `Encoding_shim_的三个_Span_重载与数组版结果一致` | `GetBytes` / `GetString` / `GetCharCount` 与数组版逐字节一致（含 4 字节代理对） |
| `StartsWith_与_Contains_的_char_重载与_string_版判定一致` | 空串 `<c>StartsWith(char)</c>` 必须是 false，不能退化成「空串匹配一切」 |
| `TryAdd_只在键不存在时写入_TryRemove_只在值匹配时移除` | 后者的语义是「键值都相等才移除」 |
| `CreateDelegate_泛型重载创建的委托可直接调用` | 反射成员可用性（netstandard2.0 只有非泛型重载） |

复测：Compat.Tests **47 → 57**（net8）/ **42 → 52**（net472）；密度 1.8% → 2.3%。
仍未覆盖的是 polyfill 的**异常**契约（如 `GetBytes` 目标 `Span` 过短时抛什么），
与 net6 的差异属于「都抛 `ArgumentException` 但时序不同」，不值得逐条钉。
